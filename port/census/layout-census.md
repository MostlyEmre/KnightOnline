# Raw-bytes layout census

Generated by `port/census/layout_census.py`. Every place the client and servers move the bytes
of an object without a field-by-field serializer, the type whose bytes move, and that type's
layout on macOS arm64, Windows x64 and Windows x86 (the original 1.298 target).

Sites by kind: copy 21, file 518, packet 404, serialize 16.

- **file**: File/FileReader/FileWriter Read and Write, fread/fwrite, ReadFile/WriteFile.
- **packet**: ByteBuffer/Packet members that copy `sizeof(T)` bytes or a buffer.
- **serialize**: memcpy and friends between a typed object and a byte buffer.
- **copy**: memcpy between two objects of the same type, in memory. Not a layout question.

Bit-fields are compared by bit offset. `src/N3Base/N3LayoutChecks.cpp`,
`src/Client/WarFare/LayoutChecks.cpp` and `src/Server/Ebenezer/LayoutChecks.cpp` are generated
from this census (`--emit`) and `static_assert` every size and offset below in every build.

Moved as bytes, but not a fixed cross-target layout, by design:

- **Table rows** (`.tbl`, `CN3TableBase<T>`): filled column by column at offsets the loader
  computes from `alignof(T)` and each column's size, using `sizeof(std::string)` for strings. It
  rejects a table whose computed row size isn't `sizeof(T)`. The rows hold `std::string`, which
  is 24 bytes in libc++ and 32 in MSVC's x64 library, so these structs differ per target and the
  loader adapts to each.
- **Packets and database blobs**: the client's `Parse_Get*` templates and the servers'
  `GetShort`/`GetDWORD`/`GetInt64`/`SetDWORD`… helpers copy fixed-width integers one field at a
  time (counted under Scalars).
- **Shared memory** between Ebenezer, Aujard and ItemManager: both sides are the same binary
  architecture, so there is no cross-target layout.
